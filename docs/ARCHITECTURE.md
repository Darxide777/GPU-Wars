# GPU Wars: architecture

GPU Wars is a standalone drag-racing simulator and GPU benchmark. It was extracted from the drag mode of Chromium Halo: Neon and keeps only what the drag game needs.

What it is **not**: there is **no city hub, no shop, no parts, no points or currency, no rivals and no 3D camera**. It has TWO game modes on one page: Drag (the quarter-mile strip, `src/drag/`) and Formula (one lap of a banked oval, `src/formula/`, see "Formula mode"); the title menu's MODE row picks one. The only views are the top-down strip (`src/drag/topdown.ts`) and the top-down oval (`src/formula/topdown.ts`). The only thing you change on the car is its **tune** (the existing tune screen and six tune slots). The car's parts are fixed at the TOP level of every part (the "stock parts"), and its power comes from the benchmark score.

## Commands

```bash
npm run build       # node build.mjs: bundles src/drag/page.ts into dist/gpuwars.js
npm run typecheck   # strict TypeScript (also flags unused locals)
npm run package     # builds and writes dist/gpuwars-itch.zip for itch.io (see docs/ITCH.md)
npm test            # builds, then runs every test in tests/ (a few seconds, CPU only)
node --test tests/<file>.test.mjs   # one test file (Node runs the TypeScript directly)
```

Play it by opening `index.html` from any static server (or the itch.io zip). `dist/` is not committed.

## The screens (`src/drag/page.ts`)

One canvas draws the strip behind a neon menu card (the Chromium Halo: Neon menu style, from `drag.html`'s CSS now in `index.html`). The card uses compact rows so the title, tune and options screens fit without scrolling at ordinary window sizes; the dyno graph is capped at its own width instead of stretching across the wide card. A new screen starts at the top, a redraw keeps the current scroll position, and `scrollIntoView` runs only after a keyboard or pad move with a small `scroll-margin`, so changing a value no longer snaps the list.

- **Title menu:** MODE (DRAG or FORMULA, first row, kept in `Save.mode`; `modeItem` in `page.ts`), BENCHMARK, CLASS, TUNE, RACE CLASS LEADER, DRIVER (MANUAL or AUTOPILOT), RECORDS, LEADERBOARD, OPTIONS, and EXIT FULLSCREEN only while the page is fullscreen (a page cannot close itself; see `docs/ITCH.md`). All rows work. BENCHMARK, CLASS, DRIVER and OPTIONS are shared; TUNE, RACE CLASS LEADER (its value is the leader's time), RECORDS and LEADERBOARD switch to the mode (a Drag-only title or row text reads the current mode). The page variable `mode` picks which branch `show()`, `frame()`, `backdrop()` and the boards use; Drag's code paths are untouched when it is `drag`.
- **Menu size:** `reserveHintSpace` in `page.ts` gives the hint line the height of the tallest description of the menu being shown (measured once per menu and card width), so hovering rows never resizes the card. It applies to every menu.
- **TUNE:** the TUNING tab (shifting, launch, boost, gears, final drive, tire pressure, ballast, fuel load, suspension, wheelie bar, nitro, REPLACE CLUTCH, REPLACE TIRES, COOL ENGINE, CLEAR STRIP, RESET TUNE, then the six tune slots at the bottom, TEST RUN) and the STATS tab (the car's numbers, the dyno graph and a predicted timeslip from a perfect-driver run). Every change is saved at once and made safe for the car (`cleanTune`).
- **RACE CLASS LEADER:** a ranked run: the fixed class day (see below) against the ghost of your class leader. A clean pass with a benchmark is sent to the leaderboard when it ends.
- **OPTIONS** (`src/options/screen.ts`): DRIVER, MUSIC VOLUME, TOUCH CONTROLS (AUTO/ON/OFF), TOUCH SIZE, ANALOG TOUCH GAS, VIBRATION, INPUT DELAY (ms), FULLSCREEN, CONTROLS FOR (keyboard or gamepad), one row per control in `BIND_ROWS` (Enter rebinds the first key or button, Right the second, Left clears the second; a key or button does one thing, so it is taken from the other control unless that would leave it with none), RESET CONTROLS. Settings are saved at once under `gpuwars.options`.
- **The race screen** (`hud.ts` `drawRunPanel`, `drawTach`, `guidePrompt`, `topdown.ts`): three things carry text during a run. (1) The LEFT PANEL (`PANEL`: row height 10 to 16 px, never wider than the gap to the tree; on a tall narrow window it stays above the car's nose when rows can stay 10 px): the stage (or the foul), reaction time and run timer, a notes block of five rows (during the run only the warnings that apply: wheelspin, hot or locked clutch, front up, nitro and shift keys; after the finish how to stop), nitro, boost, the two tire temperatures and the lane gauge. It no longer has rpm, gear, km/h or shift lamps. (2) The TACHOMETER at the BOTTOM RIGHT (`drawTach`): the round dial with the redline, rpm, gear, km/h and the five shift lamps above it, as it looked before the panel (radius 92 px x S, `TACH_HUD`; 64 px at 800x450, 92 px at 1280x720). `tachPlacement` keeps it in the corner when nothing is there; when the touch buttons, the panel, the tree, the instruction row or the cars' band (`carBand`, both lanes) are in the way it shrinks (down to `PHONE_HUD.tach.minScale`) and moves left or up, choosing the cheapest place (`shrinkCost`); with touch buttons on screen it also prefers to stay off the road (`tachObstacles` soft box), so a landscape phone puts it above the gas pedal and a portrait phone below the cars. The dial's numbers are left out when the dial is small (`numbersFromK`), never drawn under 10 px. (3) ONE INSTRUCTION LINE (`guidePrompt`, drawn by `promptBox` / `drawPrompt`) in the top row, left-aligned just right of the panel (and the touch MENU button), never under the fullscreen button; it is one short line, never two prompts, and it ends at the launch. `guidePrompt` reads the staging state the physics runs (`stagingStep` in `physics.ts`) and names the next action with the player's own bindings (`DragKeyLabels`: the page passes the bound key names, or the touch buttons' labels with `touch: true`): water box approach `HOLD W: ROLL INTO THE WATER BOX`; in the box and while cold `HOLD W + S: BURNOUT` (gas + brake, or gas + BURN on a phone); warm tires (`DRAG.tire.windowLo`) `RELEASE S: TIRES HOT`; run-out `LET OFF: STOP PAST THE TREE` until the brake distance reaches `STAGE.runOutPastTree`, then `S: STOP`, and stopped `BACK UP (R) 9 M` (metres to the pre-stage beam, only from 1 m); backing up the same, then `RELEASE R, BRAKE: STOP` when the stop would land at the pre-stage beam; stopped short of the beams `TAP W: CREEP TO PRE-STAGE`; pre-stage `TAP W: CREEP TO STAGE`; over-staged (the nose rolled past the stage beam) `BACK UP (R) TO RE-STAGE`; staged `WAIT FOR GREEN, THEN X (H: DEEP)` (the deep part only while deep staging is a real choice: at the stage beam, not over-staged, deep key bound), deep staged `WAIT FOR GREEN, THEN X`. Nothing at the green, while rolling out, at a foul or abort (the stage line says RED LIGHT / ABORT) or after the launch. Each phase lists a long text and shorter ones; the longest that fits at the minimum font is drawn. The autopilot shows only a quiet `AUTOPILOT` (never keys). NOT on the race screen (they are on the timeslip, which also lists the conditions and front, and on the TUNE stats): air, track, density altitude, wind, weather, hot and cold pressure, fuel, engine heat, weights, tire wear, splits, ET, trap, ranked or free-play banners, and every ghost word. The strip writes only the beam and mark names beside its right wall (`drawSideNames`; the gauge and the line are drawn over them if they meet on a narrow screen); the cars carry no text. The only centre text is the crash alert. The tree stays at the top middle; touch controls draw over the HUD after it, and the panel uses only the space above the first button under it, the gauge and the line stay clear of every button (`keys.avoid` = `touchLayout`). Text is never smaller than `PHONE_HUD.minFont` (10 px): when rows would need less, the panel drops rows in `PHONE_HUD.dropOrder` (lane gauge, notes to 2 rows, tires, boost, nitro, notes to 1 row; the lane gauge is always hidden under touch) and the beam names are shortened (WATER, PRE, END). `PHONE_HUD` (panel, `prompt`, `tach`) is the object to turn after a phone test; `tests/run-panel.test.mjs` checks the prompt for every phase, one line at a time, the tach corner and no overlaps at 800x450, 1280x720, 420x860, 360x640 and a touch landscape 844x390.
- **Timeslip:** the result, with RUN AGAIN, NEXT RACE, TUNE and MAIN MENU.

## The simulation (`src/drag/physics.ts`)

No drawing, no clock, no `Math.random`: `createDrag({ seed, strip, entrants })` and `step()` at `DRAG.dt` (1/240 s). The same seed gives the same race. The page picks seeds with `Math.random`; nothing inside the engine does. Weather, wind and altitude come from the seed (`conditionsForSeed`). The engine models the full staging sequence (below), the tree and red light, launch, torque curve, flywheel, clutch heat and wear, limiter, gears and shift quality, traction with suspension pitch, wheelspin and lane steering, blower boost and engine heat, nitro, fuel burn, the run-out with brake fade and chute, and a crash at the end of the strip. `AUTO_DRIVER` is an automatic driver (it also drives the whole staging sequence); the tune screen's prediction (`predictDrag`) and most tests start with `createDrag({ quickStart: true })`, which puts every car in final stage with the tree armed (the old behaviour).

### The staging sequence (`STAGE` in `physics.ts`)

`Runner.stage` (`StagePhase`) goes `waterBoxApproach` -> `burnout` -> `runOut` -> `backup` -> `preStage` -> `staged` / `deepStaged` -> `rolling` -> `launched`. Positions are metres along the strip, 0 being the final beam (the start line); the car starts at `STAGE.startX` and nothing teleports: the gas, brake, burnout and `backUp` inputs move it through a small speed model (`stagingStep`).

- **Water box** (`waterBoxStart..End`): wets the slicks (`Runner.wet`, less grip at the launch until they dry, a wet burnout heats little and lays no rubber). The water box sits just behind the start line (`waterBoxStart..End`, about -14 to -7 m) so a burnout carries on across the line and the launch lane gets fresh rubber; the autopilot keeps burning until `AUTOPILOT.burnoutPastLine`. Rubber is laid wherever the dry burnout is, also behind the line (`RUBBER.behindLine` metres of strip are kept before it), and the run-out stop (`runOutPastTree`) is past the end of the burnout.
- **Burnout:** hold gas + burnout (or gas + brake) past the box start: the car rolls at `burnoutSpeed` with the rears spinning. Heat is `heatPerSlipMetre` per metre of slip, rubber is `rubberPerMetre` per metre on the dry strip (x > 0 only), and it dries the slicks.
- **Run-out and back up:** after the burnout the car runs out past the tree, brakes to a stop, and BACK UP (new rebindable `backUp` action, default R) reverses at most `backupSpeed` with `Runner.reversing` (the reverse light). The panel shows the distance to the pre-stage beam (the speed is the panel's km/h).
- **Beams:** pre-stage `STAGE.preStageRollout`, stage `DRAG.stageRollout`, deep stage `DRAG.deepStageRollout` behind the final beam (three distinct places), and `STAGE.overstageLimit`. Gas creeps the car; in stage (`catchSpeed` or slower) the trans-brake holds it, so gas only revs. A held `deepStage` creeps from pre-stage/stage to the deep beam and stops. Creeping into the over-stage zone resets the stage bulb (`Runner.overstaged`, label OVER-STAGED) until the car backs out past the stage beam.
- **The tree** (`state.armed`, `armedAt`, `greenAt`, `treeDelay`): dark (`greenAt` is Infinity) until every live car has held still in stage for `armHold` seconds (a ghost counts when its canned path is done). Then the seed's `treeDelay` runs to the green. A live car leaving stage before the green puts the tree out and redraws the delay. Crossing the final beam before the green (or with a dark tree, reaction -1) is a red light; crossing it during the run-out is not.
- **Auto driver / ghost:** `stagingPlanFor(seed, lane, skill)` is the deterministic plan (dry burnout metres, run-out stop, back up stop, deep stage) and `aiStagingInput` drives it. For the ghost's looks, `ghostStagingPath(seed, lane, deepStage)` returns a `StagingPath` (`duration`, samples every `GHOST.step` with `x, y, v, stage, burnout, reversing`) made by running the auto driver's real staging; `stagingPoseAt(path, t)` reads it. The physics already plays it for ghost runners before the green; their ET still starts at the green. A saved ghost keeps the last `STAGE.ghostLead` seconds before the green.

### Top-fuel traction (`CLUTCH_MANAGER`, `TRACTION`)

A car with `spec.topFuel` (every GPU Wars car; the plain `specFor` car the engine tests use is not) makes far more power than its tires can hold, so the power is managed:

- **Automatic clutch manager:** the force through the clutch is capped at `use` x the grip a NOMINAL track would give (`nominalGrip`: it knows the load, the wing and tire growth but not a cold, wet, worn or badly inflated tire or a poor strip, so those still spin the car). `use = useBase + useStep x launch aggression`, and the cap ramps in from `rampStart` over `rampTime` (longer at a gentle aggression). What is held back is `Runner.managedShed`; the engine revs `managedSlip` rpm above the wheels (up to `slipRpmMax`) and the clutch heats a little (`managedHeatPerJoule`).
- **Launch rpm hold:** for `holdTime` s the slipping clutch keeps the engine near the tune's launch rpm, so a modest car launches in its power band.
- **Tire growth and the wing:** grip grows by `TRACTION.growth` by `growthSpeed`, and `TRACTION.downforceArea` presses the rear down with speed squared.
- The tune stays meaningful: launch aggression, launch rpm, final drive, tire pressure, suspension and wheelie bar all change the ET by 0.1 to 0.5 s (`tests/calibration.test.mjs`). Turn `CLUTCH_MANAGER.gripGain` and `dragGain` first (see docs/CALIBRATION.md).

### Realism (P1 of `drag-mode.txt`)

- **Air density:** `densityTorqueShare` scales engine torque by `(rho / rhoRef)^ENGINE.densityTorqueExp`; a blower with charge makes up `BOOST.densityCompensation` of the shortfall and soaks `BOOST.chargeHeatPerComp` heat for it. `densityAltitudeOf(rho)` is shown as `DA nnnM` in `conditionsText`.
- **Trap speed:** average over the last `DRAG.trapWindow` (66 ft) from the `trapStart` mark (`DRAG.marks.trapStart`) to the finish.
- **Tire pressure:** `pressureGrip(hotPsi)` has a flat peak at `TIRE.optimalHotPsi` (under it grip falls fast and the tire heats, over it falls slowly); `hotPressure(cold, tireC, airC)` adds `TIRE.psiPerC`. `Timeslip.hotPsi` (the timeslip) and the stats tab show the hot pressure.
- **Weight transfer:** the rear share gains `a x cgHeight / (g x wheelbase)` (`SUSP.transferGain`); anti-squat (`SUSP.antiSquatBase` + `antiSquatPerStep` per stiffness step) is the share the links deliver at once, the rest follows the springs over `transferTau`.
- **Shift down:** `DragInput.shiftDown` (manual shifting only) drops a gear, refused if it would pass the redline. The clutch stays automatic; nitro is automatic by gear or the nitro button.

The clutch has no key: it engages automatically. Its temperature and condition are a consumable carried between races in a visit (`clutchAfterRun`); REPLACE CLUTCH on the tune screen resets it for free. The rear slicks' wear is carried the same way (`Entrant.tireWear` in, `tireWearAfterRun` out, kept by the page for the visit, not saved); REPLACE TIRES resets it for free. A ranked run always starts with new tires.

## Formula mode (`src/formula/`)

Formula is the SECOND mode of GPU Wars: ONE LAP of a banked oval from a STANDING START against the class leader's ghost (no rivals, no weapons, no pickups, no wrecks), top-down view only, tuning only (no shop). It was extracted from Chromium Halo: Neon's formula car Race, where it is a flag (`race.opts.sim`) on the Arena's driving engine; here it is its own pure module. **Phase 1 is the simulation, the autopilot, the ghost and the picture; phase 2 (the page wiring, below) connects it to the game.** The lap times are not calibrated per class and score yet (phase 3). The simulation files in `src/formula/` import nothing from Drag, the backend or the page, and a test checks they use no `Math.random`, clock or page object (`page.ts`, `model.ts` and `online.ts` are the page layer and are exempt from the clock and canvas rules, not from the `Math.random` rule).

**The API a page uses** (`src/formula/index.ts`):

```ts
const race = createFormulaRace({ track, spec, tune, ghost });  // track: trackById('beach'); spec: formulaSpecForBenchmark(save.benchmark); tune: the saved tune; ghost: ghostFromLeader(...) or null
race.step(input);          // one FIXED step (FORMULA_DT = 1/60 s); input is a FormulaInput { throttle, brake, steer, shiftUp, shiftDown, nitro } (a DriverInput fits: shifts are presses)
const v = race.view();     // FormulaView: lights, race and lap clocks, sector, car (gear, rev, shiftLight, kmh...), ghost pose and gap, timeslip
draw(ctx, W, H, v, { showLine, line: racingLineFor(spec, tune, track), time, showDelta });  // the top-down picture and the lap HUD
race.timeslip();           // FormulaTimeslip { reaction, lapTime, splits, sectors, launchTime, topSpeed (km/h), wallHits, valid, jumpStart }
race.trace();              // the lap recorded so far, as a compact LapTrace; ghostFromLap(track, slip, trace, name) turns a finished clean lap into a ghost
predictFormula(spec, tune, track);   // the tune screen's predicted timeslip (the autopilot's lap; cached, about 0.1 s the first time)
const ap = createFormulaAutopilot(race.track, race.state.car.stats); race.step(ap.decide(race.view()));  // the autopilot: same FormulaInput; leaderboard category AUTOPILOT_CATEGORY = 'autopilot'
```

- **The physics is ONE pure function**, `driveStep(car, input, track, dt)` in `physics.ts`: car in, car out, nothing mutated. It is the Arena's `driveCar` with its race-simulation flag on (`grip.ts` too), kept at the same numbers: single-number grip (`gripLimit`: base grip plus downforce times speed squared; a turn is limited to it and braking shares it), banking (`bankedLimit`: more grip turning toward the inside), hills (grade takes speed off uphill), the manual gearbox (`gearPull`: seven gears, `GEAR_TOPS`, best in the top of a gear's range, cut at the limiter) with `shiftLightOn`, the wall (`roadHit`: scrubs to `GRIP.wallKeep` of the speed above `GRIP.wallScrub` m/s, counted in `wallHits`). **Same inputs give the same lap to the step as the source game** (checked by a test; `tests/formula-autopilot.test.mjs` runs the live source when its folder is present). Turn `BASE` and `GRIP` (`constants.ts`) first. The brake pedal is also reverse (as in the source game): the lap lets it go once the car has stopped.
- **The lap** (`race.ts`, `stepLap` is pure too): 3 lights one a second, green at `LIGHTS.go` (3.9 s); the car is held until then; gas before the green is a JUMP START (`valid` false, never ranked). The lap is **timed from the start line** (first crossing of gate 0 starts it, the next crossing finishes it; gates must be crossed in order and are the sector splits), the **reaction** is green to first gas, and the car rolls out braking for `LAP.rolloutSeconds` after the finish. `LAP.maxSeconds` makes a stuck car a DNF (`timeout`). `laps` (default 1) exists so the racing line can be worked out over two.
- **The car** (`car.ts`): `STOCK_SPEC` is the TOP level of every part. `carStats(spec, tune)` is the source's `raceCarStats`. The tune (`FormulaTune`: gearing, downforce, steering, pressure, nitro bottles 0 to 3, gearbox manual/auto, shift light) is made safe by `cleanFormulaTune` (every range, steps of 0.1, whole bottles, NaN and strings fall back to the default; a hostile tune equals the edge-of-the-limits car, tested); `cleanFormulaSlots` runs the six tune slots (`src/tune-slots.ts`) through it, `FORMULA_TUNE_HELP` has a line per row. Nitro is new in Formula (the source had none): `NITRO` in `constants.ts`. An automatic gearbox shifts at the shift light (`AUTO_GEARBOX`).
- **The benchmark sets the power** (`formulaSpecForBenchmark`, CALIBRATED in phase 3): the score as a share of the class cap goes through `FORMULA_SCORE_TO_ENGINE` (like Drag's `BENCHMARK_TO_SPEC`) to a place inside `FORMULA_CLASS_WINDOWS` (the engine level of the slowest card and of the class cap: integrated -1.44 to 3.55, discrete 4.47 to 8, the source's top engine); no benchmark is `UNBENCHMARKED_ENGINE` (-2.54), slower than every benchmarked car. Default-tune autopilot laps on BEACH: best discrete 38.1 s, the Radeon 8060S 47.0 s, the S24 Ultra 51.0 s, the weakest integrated card 55.0 s, no benchmark 58.0 s (the table and how to turn it: docs/CALIBRATION.md, "Formula lap times"). **The tune** (`TUNE_EFFECT` in `constants.ts`) was rebalanced: gearing and tyre pressure have a best value inside their range, so a good tune is worth 2 to 3.5 percent of the lap (the source game's tune was a straight line worth 10 percent).
- **Tracks are data** (`tracks.ts`): a `TrackSpec` (control points, width, lap length, margin, gate count, banking, hills, grid place) goes in `TRACK_SPECS`; `buildTrack` makes the road, gates and grid. BEACH is the source's `oval` (3 miles, 24 m wide, banked 31 degrees, 7 gates). MONACO and MOUNTAIN from the source can come back as more specs (the road code already does hills; open roads, ramps, loops and shortcuts were left out).
- **The autopilot** (`autopilot.ts`) is the source's ACE BOT (the race simulation branch of `raceBot.ts`): follow the middle line aiming `AUTOPILOT.aim` points ahead, look `brakeLook` points down the road and be slow enough for each bend (`cornerSpeed`), keep off the wall; plus a reaction time (`AUTOPILOT.reaction`), manual shifting and nitro. It laps within 0.4 percent of the source bot on six car and tune combinations (the test allows 3 percent). `driveAutopilotLap(options)` runs a whole lap.
- **The racing line** (`racingLine.ts`): the autopilot's second (flying) lap of two, a point about every 3 to 5 m with what it did (`LINE.green` accelerate, `yellow` lifting or a braking zone ahead, `red` braking). On BEACH the cars take every bend flat out, so there is no red. `solveLap` caches the two-lap run, which also gives `predictFormula`'s timeslip.
- **The ghost** (`ghost.ts`): a compact **LapTrace** `{ step, s, o, v }`: every 0.1 s from the green, along the lap, across the road and speed, in whole decimetres (about 6 KB of JSON). `ghostFromLap` makes one from a clean lap; `ghostFromLeader(track, { name, lapTime, splits?, reaction?, topSpeed? })` MAKES UP a lap that crosses the start line, every gate and the finish at the leader's times (monotone curve, seeded wander across the road, no `Math.random`; missing splits come from `defaultSplits`); `ghostPose(ghost, track, t)` replays it and `ghostTimeAt` gives the gap. `cleanGhost` makes a saved or sent ghost safe or refuses it. Turn `GHOST.launchAccel` first if made-up ghosts leave the grid too slowly or quickly.
- **The picture** (`topdown.ts`, `hud.ts`): north-up camera on your car, pulling back with speed, the oval with cyan left and magenta right edges, banking bars, the sea, a chequered start line and yellow sector gates, your car, the see-through ghost car, the optional racing line (`showLine` + `line`), a small map of the whole oval bottom left. Text is only the HUD, in the style of Drag's: the LEFT PANEL (state, lap clock, sector, last split, nitro, and the gap to the ghost only with `showDelta`: Drag keeps ghost words off the race screen), the three START LIGHTS at the top middle, the GEAR BOX bottom right (gear, km/h, five shift lamps that all blink at the shift light). Never under `HUD.minFont` (10 px). The page must draw touch buttons over it and keep clear of them (phase 2).
- **Phase 2: the page (done).** One page, one bundle: `src/drag/page.ts` stays the build entry and imports `createFormulaMode` from `src/formula/page.ts`; the title menu's MODE row sets `mode` (kept in the save). `src/formula/page.ts` is given a `FormulaHost` (the save, the options, the input, the sfx, the pad, the leaderboard's `FormulaOnline`) and returns what Formula needs: `tuneItems` (the FORMULA TUNE rows: PREDICTED LAP from `predictFormula`, gearing, downforce, steering, tyre pressure, nitro bottles, gearbox, shift light, RESET TUNE, the six slots from `src/tune-slots-menu.ts`, TEST RUN; **no REPLACE TIRES, the car has no tyre wear**), `statsHtml` (the STATS tab), `raceItem`, `start`, `frame` (the fixed `FORMULA_DT` steps, the three light beeps and the green, the lift-off sound, the engine loops, the end of the lap), `drawFrame`, `slipView` (the timeslip: reaction, launch, every sector, lap time, top speed, wall hits beside the leader's, then the VS deltas, the personal bests broken, the leaderboard status) and `recordsHtml`. The flow is title -> FORMULA TUNE -> race (lights, one lap, rolling out) -> timeslip (RUN AGAIN, TUNE, MAIN MENU); RACE CLASS LEADER is a ranked lap (the ghost of the class leader, sent when clean), TEST RUN is a free lap with no ghost and nothing sent.
- **Input (Formula):** `input.readFormula(FORMULA_DT)` returns `FormulaDriverInput` (`toFormulaInput` in `src/input/controls.ts`): gas and the analog pedal, brake (1 or 0), steer (keys, the touch buttons, the stick or d-pad), nitro held, and shift up and shift down as ONE press each (a held key shifts once; the Drag mapping's "launch also shifts up" does not apply: Enter and the launch key do nothing in Formula), plus `toggleLine`. - **The autopilot** drives a Formula lap through `createFormulaAutopilot(...).decide(view)` (the same FormulaInput); its leaderboard category is `autopilot`, it is sent like a manual lap and skips the local records (as in Drag). The category is the DRIVER option (`options.driver`), not `lb.category`.

## The benchmark, the class and the car's numbers

**BENCHMARK** (title row, never automatic) opens `src/benchmark/screen.ts`: a full-window NEON layer: the workload's canvas fills the window (CSS `object-fit: cover`) under cheap CSS overlays (a neon frame, a perspective grid, scanlines; compositor-only, they do not change what the card is measured on), the song title (SIMULATION THEORY, cyan glow) and band (CHROMIUM HALO, magenta glow) big top-left, pulsing with the beat through the CSS variable `--pulse` (a wider glow, never a flash), the status line, a thin progress bar and CANCEL (Esc does the same). Responsive for phones in portrait and landscape. `workload.ts` draws a fixed 1280x720 Julia-set shader pulsing with the beat in the game's palette (`PALETTE`: #05010f, #ff2bd6, #21e6ff; no equalizer, no full-screen flashes); it tries WebGL2, then WebGL1, then a 2D canvas (whose score is limited, `canvas2dScoreShare`). `runner.ts` does a warm-up, then `passes` timed passes (about 12 s), syncing with a one-pixel read-back so the card has really finished. The scored work (`BENCHMARK` numbers and the shader source) is pinned by a test: change it only with a `version` bump and a recalibration. THE SHOW PHASE: after the score is computed, if a song is playing (`RunDeps.song`), the screen stays up until the song ends (286.8 s): `workload.lighten()` shrinks the canvas to `SHOW` (640x360) and `workload.draw()` makes ONE draw per animation frame, at most one every `SHOW.frameMs`, with no read-back, so the card and a phone stay cool; the status reads SCORE LOCKED IN, SONG m:ss / m:ss, ESC SKIPS TO THE RESULT. Esc or CANCEL in the show phase delivers the already measured score; during the timed run it cancels as before. With no song (music volume 0, blocked autoplay, a failed file) there is no show phase. A stalled song is given up on `SHOW.graceSeconds` after its length. `score.ts` throws away passes slower than the median by `throttleDrop` (or faster by `spikeRise`), refuses a run whose passes took an implausible time or that was hidden, turns the mean rate into a log-scale score (0 to `maxScore`) and caps it by class. All tunables are the one `BENCHMARK` object in `constants.ts` (`warmupMs`, `passes`, `throttleDrop`, `version`, and the `rate` ranges to calibrate on real cards). Change `version` whenever the workload or scoring changes. The result screen and the console print the CALIBRATION LINE (`calibrationLine` in `score.ts`: raw score, kept score, class cap, mean work rate in units/s); `docs/CALIBRATION.md` says how to turn it into `BENCHMARK.rate` numbers.

**The card and the class** (`gpu.ts`, `rules.ts`, `menu.ts`): the class is **never picked**; the game detects it, always (`GpuIdentity.gpuClass` is a real class id, never null). `readGpuIdentity` collects WebGL's unmasked vendor and renderer (from a context with the benchmark's own options) and WebGPU's adapter info (vendor, architecture, device, description, `isFallbackAdapter`); `identify` turns them into one class. There are only TWO classes (`integrated` and `discrete`), so each reading becomes a verdict of just built in or separate (and how plain the evidence is) from tables: every GeForce, Quadro, RTX and GTX is separate, Radeon RX by number, `gfx` ids and codenames that Mesa prints (gfx1151 is Strix Halo and built in; gfx1100 and gfx1201 are cards), the built-in parts (Radeon 610M to 890M, 8040S to 8060S, Vega 3 to 11, `Radeon Graphics`, RDNA 3.5), Intel UHD/HD/Iris/Xe/"Arc Graphics" built in and Arc A/B-series separate, Apple, Adreno, Mali and the software renderers (SwiftShader, llvmpipe) built in. WebGL (the card that is timed) wins ties; plain evidence beats a guess; a WebGPU fallback adapter does not veto a real WebGL card. **Masked names:** browsers that hide the card report a fixed placeholder (`AMD Radeon R9 200 Series, or similar`, `NVIDIA GeForce GTX 980`, `Intel(R) HD Graphics`, `Mozilla`, `Generic Renderer`, `ANGLE (Google, Vulkan ...`; sources in the comment in `gpu.ts`), or WebGL and WebGPU strongly disagree. `identify` then sets `GpuIdentity.masked`, the class is the default INTEGRATED, and the benchmark (`startBenchmark({ masked })`, `outcomeFromPasses`) decides the class from the measured rate with `MASKED_GPU_RULE` (`constants.ts`: the measured 8060S rate x margin 2; `classForMaskedRate` in `score.ts`). The result stores `classFromSpeed: true`; `rerunReason`/`repairBenchmark` do not compare that class with the pre-benchmark default (no loop), still drop a result whose class is faster than its score supports, and `resultFromRun` caps the score to its class. The console line and BENCHMARK DONE screen add `MASKED_NOTE`. See docs/CALIBRATION.md. **Safe defaults when it is unclear (documented in `gpu.ts`): integrated-or-separate unknown means INTEGRATED (a strong iGPU is never raced as a discrete card; only plain evidence of a separate card makes it discrete).** The maker and generation are not looked at any more (they come back only if classes are added). The result screen and the console print `GPU SEEN: <the id> | CLASS: <class> (why)` (the raw GPU string is always shown). The CLASS row of the title menu only shows the detected class (no arrows, no ENTER). The benchmark can only start in the detected class and waits until the card has been read. The result `{ score, class, benchmarkVersion, gpuId, date, sustain? }` is re-run only when `gpuId`, `benchmarkVersion` or the detected class changes (`rerunReason`); a saved result whose class differs from the detected one (an old hand-picked class) is thrown away on load (`repairBenchmark`) and the car is stock until the benchmark is run again. A save from the 17-class build holds an id such as `discrete-nvidia-classic`: `cleanBenchmark` keeps it (any plain id), so it reads as 'class changed' (the page says so, drops the result and asks for a re-run); `specForBenchmark` treats an unknown class as no result (the weakest car), never a faster one.

**The car's numbers.** `src/drag/spec-source.ts` is the one place a race or the tune screen gets the car's spec:

```ts
specForBenchmark(benchmark: BenchmarkResult | null, clutchCondition = 1): DragSpec
```

With no result it is the WEAKEST spec (integrated, score 0, and 10% less torque than that card, so it is slower than every benchmarked car, about 13 s). With one, the spec is made in two steps so each class has a lot of room and the score still matters inside it: the score is taken as a share of the class's top score (`classScoreCap`), and `BENCHMARK_TO_SPEC` turns that share into where in the class's window (`CLASS_SPEC_LIMITS`: peak torque and limiter at the bottom and top of the class) the engine sits. The windows are what separate the classes: integrated 360-640 Nm (a 12.3 to 9.4 s car, the class's top score is 80 percent of `maxScore`) and discrete 1400-6500 Nm (one wide window: a 6.9 s funny car for the weakest old card to a 4.0 s top fuel car for the best current one; the log score scale spreads real cards over it, `docs/CALIBRATION.md`). The result's `sustain` picks the torque curve between `CURVE_BURST` and `CURVE_SUSTAINED`. `finalDriveFor(torque)` is the default final drive (short for a weak engine, tall for a strong one) and `readyCar` builds the default tune from it and from `LAUNCH_RPM_SHARE`. The curve lives on the spec (`spec.curve`, used by `torqueShape`). `stockSpec()` is a top-fuel-style car (`spec.topFuel`, see below): the stock car's grip and drag area times `CLUTCH_MANAGER.gripGain` and `dragGain`. `src/benchmark/dyno.ts` draws the same curve (hp = Nm x rpm / 7127, at the flywheel before the blower's boost) as the graph on the STATS tab, with the shift point and the power peak; the timeslip shows hp. It is a pure function of the saved result. `readyCar(save, clutchCondition)` in `model.ts` calls it and adds the tune (the default tune is built from the engine's own revs).

## The save (`src/save.ts`)

One small versioned record under the key `gpuwars.save`, repaired on load (`sanitizeSave`; version 2 has no `classLock`, an older save's lock is dropped; version 3 adds `mode` and `formula`, see "Formula mode"): `mode`, `formula` (Formula's tune, slots and records), `benchmark` (`{ score, class, benchmarkVersion, gpuId, date, sustain? }` or null), `tune`, `slots` (six) and `records` (totals, bests, the last ten runs; plain records, no ghost of your own). Settings are kept apart (`gpuwars.options`; they include the `drivingLine` option) so erasing a save never loses your controls. All storage goes through `src/browser-store.ts`, which never throws and falls back to memory when localStorage is blocked.

## Extension points for the next phases

- **Input:** `readInput()` in `page.ts` is one line: `race.setInput(0, options.driver === 'autopilot' ? autopilot.decide(viewOf(race, 0, phase)) : input.read())`. Keys, touch pointers and pad polls are pushed as timestamped events (`src/input/queue.ts`); each fixed tick drains the events due by that tick's time and builds a `DriverInput`. Touch controls are drawn on the canvas by `input.draw()` (`touch.ts`). Haptics buzz on launch, shift, nitro, wheelspin, wheelie, chute, foul, wall and crash.
- **Autopilot** (`src/drag/autopilot.ts`): `decide(viewOf(race, 0, runner.stage))` returns a `DriverInput`. It never works out the staging itself: the page passes the engine's `StagePhase`, and each phase gets what a player would press. `waterBoxApproach` and `burnout`: gas to the water box, then gas + burnout (shorter when the engine is hot, until the tires reach `burnoutTireTemp`), then gas on. `runOut`: gas until the car would stop past the tree, brake, then back up. `backup`: back up to just behind the pre-stage beam, brake, then creep (`creepGas`). `preStage`: creep into stage (the engine holds a slow car there). `staged`: full gas, and `launch` (roll out) at the moment that puts the car on the final beam `AUTOPILOT.reaction` seconds after the predicted green, read from the ambers. After `launched`: `autoThrottle`, shifts, nitro and the chute. A shift point at the limiter is brought down by `SHIFT_POINT.lampRpm` (`tune.ts`), so the limiter lift cannot hold either the automatic tune or the autopilot's manual press just under its own shift point. It pays the full staging (about 30 s of the race clock) but the ET starts at the launch, so that does not change it. `page.ts` sets the leaderboard category with `lb.setCategory` (`syncCategory`), so autopilot runs race the autopilot leader on the same ranked class day, and they skip local records.
- **Adding a class later (a vendor or generation split):** the list is ONE file, `backend/src/classes.ts` (`CLASS_IDS`, `CLASS_BOUNDS`); the game imports it, so nothing is copied. Then add a row for the id in `CLASS_SPEC_LIMITS` (`spec-source.ts`), `CLASS_SCORE_SHARE` (`benchmark/constants.ts`), `CLASS_LABELS` and `CLASS_NOTES` (`src/classes.ts`), `FALLBACK_LEADERS.classEt` (`leader.ts`), `powerByClass` (`ghost.ts`) and the bands in `tests/calibration.test.mjs`, teach `src/benchmark/gpu.ts` to tell the classes apart, and write a migration if rows of an old id exist (see `backend/migrations/0002_two_classes.sql`). Then `npm run migrate:remote` and `npm run deploy` in `backend/`.
- **Leaderboard server:** `backend/` (Cloudflare Workers and D1); its public address is `LEADERBOARD_API.baseUrl` (run `npm run migrate:remote` and then `npm run deploy` in `backend/` to ship changes such as new class bounds or a migration). Reads (`GET`) allow any origin and are cacheable for 10 s, writes only the allowed origins (`backend/src/index.ts`).

- Staging uses the speed model in `stagingStep`, not the drivetrain: the clutch and engine temperature only see the revs and the heat from the gas, as before.
- `topdown.ts` uses `Math.random` for the look of tire smoke puffs (drawing only, not the simulation); it should move to a seeded source so replays look identical.
- The input delay only delays delivery of presses; it cannot move a press earlier than the frame it arrived in.
- Per-run tire wear that the source charged points for is gone: tires start every race new (the live per-run wear inside a race is unchanged).
- Formula: the first time the DRIVING LINE is drawn (or the PREDICTED LAP is shown) the lap is solved, about 0.1 s, then cached; on a slow phone that can be one visible hitch. Nothing in Formula's page has been judged on screen (looks, feel, touch layout, sounds): the owner does that in a browser.
